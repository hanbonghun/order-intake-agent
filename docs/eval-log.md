# 평가 개선 이력

각 항목은 "가설 → 변경 → 수치 변화 → 남은 실패"로 기록한다.
수치는 `uv run python -m evals.run --compare <이전> <이후>` 출력에서 옮긴다.

---

## v0 — 기준선 (2026-10-17)
- 변경: 평가 파이프라인 구축. dummy(아무것도 안 함) / oracle(정답 반환) 실행기로 채점 로직 검증
- 데이터: 깨끗한 발주 30건 (이메일 15, PDF 10, 엑셀 5)
- 수치: dummy 전 지표 0, oracle 전 지표 1.0 → 채점 로직 정상
- 관찰: 시드 적재 후 `similarity('흰우유 1L', '우유') = 0.11`. 짧은 한글 품목명에서 trgm이 약할 수 있음 → 검색 검증 단계에서 확인

## v1 — 파서 + classify + extract (2026-10-17)
- 가설: 깨끗한 발주는 structured output 추출만으로 헤더 필드와 품목 구조를 거의 완벽히 얻을 수 있다
- 변경: 본문·PDF·엑셀 파서, classify(gpt-5.4-nano), extract(gpt-5.4-mini), identify_customer(이메일 조회 + 기본 배송지). 매칭·검증은 임시 노드
- 수치 (30건)
  - 분류 1.000, 거래처 1.000, 납기 1.000, 배송지 1.000
  - 품목 매칭 0 (임시 노드라 정상). 대신 trace의 추출 품목을 정답과 대조: **97개 중 97개 품목명·수량·단위 일치**
  - 평균 1,338 토큰, 2.5초, $0.001 / 건
- 모델 비교 (참고, 정식 기록 아님)
  - qwen3:8b (Ollama, M1 16GB): 3건 스모크 테스트에서 필드 전부 일치. 25건 진행 시점 평균 약 46초/건으로 중단
  - 느린 원인은 메모리 부족(스왑 15GB 사용). JSON 스키마 제약은 원인이 아니었다 (json_schema 6.8 tok/s > function_calling 3.8 tok/s)
  - → 개발은 API 모델로 진행하고, 로컬 모델 비교는 메모리 여유가 있는 환경에서 다시 측정
- 다음: match_products (별칭 정확 일치 + 단위 정규화 "box"→"박스" + 단위 환산)
