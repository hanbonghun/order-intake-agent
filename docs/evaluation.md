# 평가

## 원칙

- **정답을 먼저 만들고 문서는 나중에**: 정답 주문 JSON을 만든 뒤 이메일·PDF·엑셀로 렌더링해 라벨이 처음부터 정확하게 했다
- **운영과 같은 경로로 실행**: 모든 케이스를 실제 메일 원본(.eml)으로 만들어 MIME 파싱 → 수신 처리 → 그래프를 거친다. 케이스마다 DB를 시드 상태로 초기화한다
- **결과를 코드 버전과 연결**: 평가 결과마다 실행 시작 시점의 커밋 해시를 기록하고, 주요 버전은 `eval-vN` 태그를 단다
- **hold-out은 측정에만**: 개선에 쓰지 않은 케이스를 따로 두고, 그 실패를 보고 코드를 고치지 않는다

### 라벨링 기준

시스템이 어떻게 동작하는지가 아니라 **"꼼꼼한 직원이라면 어떻게 처리할지"**가 기준이다.

| 정답 | 조건 |
|---|---|
| create | 상품 마스터와 거래처 주문 이력만으로 확정 가능 (오타, 미등록 표현, 이력으로 알 수 있는 단위 누락) |
| inquire | 거래처만 답할 수 있음 (납기 누락, 진짜로 애매한 품목, 미취급 상품, 이력 없는 단위 누락) |
| review | 내부 판단 필요 (재고 부족, 발신자 확인 불가) |
| skip | 발주 아님 |

정답 품목에는 "확정 가능한 품목"만 넣는다. 거래처에 물어야 하는 품목은 제외한다.

## 지표

| 지표 | 정의 |
|---|---|
| 분류 정확도 | 발주 / 비발주 판별 |
| decision 정확도 | 최종 처리 상태(create / inquire / review / reject / skip)가 정답과 일치 |
| 필드 정확도 | 거래처, 납기, 배송지 각각 |
| 품목 재현율·정밀도 | `sku + 수량 + 단위 + 기본 단위 환산 수량`이 모두 맞아야 정답 |
| 주문 완전 일치 | 필드와 품목이 빠짐·추가 없이 모두 일치 |
| 자동 처리율 | 발주 중 사람·거래처 개입 없이 등록된 비율 |
| **오등록률** | 자동 등록했는데 등록하면 안 되는 건이었거나 내용이 틀린 비율 (가장 중요) |
| 회신 전 결정 정확도 | 재질의·검토 시나리오에서 첫 결정이 맞았는지 |
| 후속 발주 정확도 | 검토 승인으로 학습한 별칭 덕분에 후속 발주가 resolver 없이 처리됐는지 |
| 토큰·지연·비용 | 노드별 사용량 합계 (LangSmith 집계와 일치 확인) |

```bash
uv run python -m evals.run --runner oracle              # 채점 로직 검증 (전부 1.0이어야 함)
uv run python -m evals.run --runner graph --tag v9      # 실행 → evals/runs/v9.json
uv run python -m evals.run --compare v8 v9
```

## 임계값 실험

77건 평가셋에서는 resolver 확정 품목이 약 20개이고 모두 거래처 이력 근거로 확정돼, 점수 차 임계값이 결과에 영향을 주지 않았다. 그래서 품목 단위 벤치마크를 따로 만들었다.

- **구성 (129개)**: 미등록 표현 91개(같은 표현을 그 상품 이력이 있는 / 없는 거래처로 각각), 일반 명칭 30개("시럽", "원두" 등: 이력에 해당 계열이 하나면 그 상품, 아니면 거래처 확인), 미취급 8개
- **방법**: resolver(LLM)는 한 번만 실행해 결과와 신호 재료를 기록($0.54, 70초)하고, 판정 정책은 오프라인으로 재생해 비교 → 정책마다 LLM을 다시 부르지 않고 결과가 결정적

| 정책 | 자동 확정 | 오확정 |
|---|---|---|
| 검색 1위 점수 ≥ 0.5 (LLM 없음) | 41% | 7건 |
| 검색 1위 점수 ≥ 0.6 (LLM 없음) | 17% | 0건 |
| LLM 판단만 | 84% | 7건 |
| LLM + 규칙 (이전: 점수 차 0.15, 경쟁 gap 0.15) | 62% | 0건 |
| **LLM + 규칙 (현재: 점수 차 0.15, 경쟁 gap 0.1)** | **68%** | **0건** |
| LLM + 규칙 (점수 차 0.1, 경쟁 gap 0.1) | 74% | 0건 |
| LLM + 규칙 (이력 경쟁 검사 끔) | 71% | 2건 |

![판정 정책별 자동 확정률과 오확정률](images/threshold_tradeoff.png)

- LLM 판단만의 오확정 7건은 모두 일반 명칭("우유", "원두", "생크림")이었다. 거래처가 주문한 적 없는(또는 여러 개 주문한) 상품을 글자상 가장 가까운 것으로 골랐고, 규칙이 7건 모두 막았다
- 이력 경쟁 검사는 "원두" 오확정 2건을 막는다. 다만 gap 0.15는 "녹차라떼 파우더"처럼 구분어가 있어도 보류할 만큼 보수적이어서 0.1로 조정했다
- 점수 차 0.1이 자동 확정은 더 높지만, 가장 가까운 오확정 사례("생크림" 1·2위 차 0.071)와의 여유가 0.029뿐이라 0.15를 유지했다
- 이 벤치마크로 고른 값이므로 같은 벤치마크 수치는 낙관적이다. 전체 77건 재실행(v8)에서 회귀 없음을 확인했다

```bash
uv run python -m scripts.build_matching_bench       # 벤치마크 생성
uv run python -m evals.matching_bench --tag bench-v1 # resolver 실행·기록
uv run python -m evals.policy_sweep --run bench-v1   # 정책 비교 (오프라인)
uv run python -m evals.plot_tradeoff --run bench-v1  # 차트
```

## 개발 중 발견한 문제

평가와 실제 연동에서 발견해 고친 것들. 자세한 내용은 [eval-log.md](eval-log.md).

| 문제 | 발견 경로 | 조치 |
|---|---|---|
| resolver 프롬프트 예시가 평가 케이스와 같음 (정답 누수) | 결과 검토 | 일반 표현으로 교체 후 재측정 |
| 검토자가 수량만 고친 품목도 별칭으로 저장 | 검토 시나리오 trace | 상품을 바꾼 경우만 학습, 이미 정확 일치하는 표현 제외 |
| 회신 해석 결과 단위가 "박스 (24개입)"처럼 선택지 문구를 포함 | 반복 실행 중 LLM 변동 | 단위 정규화에서 괄호·조사 제거 |
| 사람이 메일함을 함께 보면 회신이 먼저 읽음 처리되어 폴러가 놓침 | 실제 Gmail 시연 | 읽음 표시 대신 UID 커서로 처리 여부 판단 |
| 처음 연결한 계정이 개인 메일함 | 실제 연동 준비 | 폴러가 시작 이후 도착분만 처리, 발신자 제한 옵션 |

## 한계

- **규모**: 77건 + hold-out 12건 + 벤치마크 129개는 작다. 품목 하나 실패가 decision 정확도 약 1.3%p
- **작성자 편향**: 평가 케이스 대부분과 시스템을 같은 작성자(개발자와 LLM)가 만들었고, 개선은 이 평가셋의 실패를 보고 했다. hold-out도 문장을 쓴 모델과 추출 모델이 같다(gpt-5.4-mini)
- **실데이터 미검증**: 실제 거래처 발주로 검증하지 않았다
- **LLM 변동**: 같은 케이스도 실행마다 결과가 달라질 수 있다. 반복 실행으로 분산을 측정하지 않았다
